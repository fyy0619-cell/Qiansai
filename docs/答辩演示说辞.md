# 答辩演示说辞 —— 基于多模态感知的智能汽车无感交互与安防系统

> 全国嵌入式大赛复赛答辩测评用稿。建议主讲时长 8–10 分钟，配合实物 / 视频演示；末尾附**演示节奏表**与**答辩问答预案**。
> 括号内为【舞台提示】，不必念出。可按现场时间弹性删减，加粗句为必讲要点。

## 一、开场（约 40 秒）

各位评委老师好！我们的参赛作品是 **《基于多模态感知的智能汽车无感交互与安防系统》**。

先请老师们设想两个日常场景：一是**双手拎满东西走到车边，却还要腾出手掏钥匙、按遥控**；二是**车停在路边被剐蹭，车主却毫不知情，事后也找不到证据**。今天这套系统，就是要让车"**认得出主人、看得清周围、还能主动报警**"——**人不掏钥匙、不碰车，走近即开、走远即锁；有人越界，自动取证；车被剐蹭，微信秒级预警**。

我们把它凝练成一句话：**以「UWB + 毫米波雷达」的"身份—位置"融合鉴权为核心，做真正无感的车门交互，并配套一套分布式多模态安防系统。**

---

## 二、选题背景与痛点（约 50 秒）

当前市面上的无钥匙进入方案，普遍存在三个痛点：

1. **"无感"不彻底**——遥控钥匙要按键、手机蓝牙钥匙要掏手机、解锁还有明显延迟，本质仍是"半接触"。
2. **易被"蹭开门"**——传统方案只判断"钥匙信号在不在附近"，**分不清靠近的到底是不是车主本人**，存在中继攻击、陌生人贴身蹭开的安全隐患。
3. **安防是"被动"的**——多数只在事后调记录，**车主不在场时无法第一时间知情**。

我们的核心思路是：**用多模态传感器融合，把"是谁"和"在哪"这两件事同时解决**，从根上解决"无感"和"防蹭"的矛盾，并把被动记录升级为主动预警。

---

## 三、系统总体方案（约 1 分 30 秒）

【舞台提示：切到系统架构图 / docs 中的框图】

整个系统采用**三层分布式架构**，职责清晰、算力分层：

- **感知层**——**6 块 ESP32** 分工协作：3 块各挂一个**毫米波雷达**分装车身不同角度探测行人坐标；1 块 anchor 作为**车端主控大脑**，集成 **UWB 测距 + MPU6050 擦碰检测**；1 块 tag 是**车主随身标签**（电子钥匙）；1 块负责**擦碰事件上云**。
- **中枢层**——**树莓派 5**，跑 Qt 车载 UI、任务调度和 Python 人脸识别。
- **执行层**——继电器门锁、四路摄像头、WS2812 状态灯、ThingsCloud 云平台。

**一句话数据流**：3 个雷达测到车周行人坐标，经 **BLE 菊花链逐级级联**汇聚到主控 anchor；anchor 再用 **UWB 判断"是不是车主本人在靠近"**、用 **IMU 判断"是否被剐蹭"**；融合后经**串口**上传树莓派；树莓派做 UI 显示与调度，触发**开关门、分区录像、云端预警**。

这样的分层设计，让**低算力的 ESP32 专注实时采集与预处理，高算力的树莓派专注识别与决策**，既保证实时性，又留足扩展空间。

## 四、功能演示讲解（约 2 分 30 秒）

【舞台提示：这一段边演示边讲，建议按下面顺序做实机 / 视频演示】

我们实现了**六大功能**，覆盖"无感交互"与"主动安防"两条主线：

**功能 1｜无感开关车门（核心体验）**
车主带着 UWB 标签走近，**距车约 1 米自动开门；走远约 2 米以上自动落锁**。全程不掏钥匙、不碰车。
【演示：人带标签走近→门开、绿灯亮；走远→门锁、红灯亮】

**功能 2｜电子围栏 + 分区自动取证**
车周划定电子围栏，**陌生人越线即自动唤醒对应方位摄像头录音录像并留存**。
【演示：陌生人越过警戒线→Qt 界面对应象限摄像头点亮、开始录像】

**功能 3｜人脸识别开门**
标签万一没带 / 没电，车主**刷脸即可开门**；识别为车主时，刚才越界触发录下的视频会**自动删除**（车主不算入侵）。
【演示：车主正脸→识别通过→开门】

**功能 4｜NFC 刷卡 / 车钥匙按键开门**
再加一层兜底：**授权 NFC 卡一刷即开**，或直接按 tag 上的按键开关门。

**功能 5｜剐蹭主动预警**
车辆静止被剐蹭，**IMU 检测到加速度突变**，立即经云平台**推送微信预警**，车主人不在车旁也能秒级知情。
【演示：轻拍/晃动车模→手机微信收到预警】

**功能 6｜车载 Qt 可视化 UI**
一块屏实时显示：**车门状态、车周行人实时坐标、四路摄像头开关状态、以及录像回放**，信息一目了然。

**至此，从"人—车交互"到"车—环境安防"，形成了一个闭环。**

## 五、核心创新点（约 2 分 30 秒，答辩得分关键段）

【舞台提示：这是评委最关注的部分，语速放慢、重点突出】

**创新一：多模态融合的"身份 + 位置"双重鉴权——这是本作品区别于普通无钥匙进入的本质创新。**
- **UWB 负责"是谁"**：通过车主随身标签做**厘米级双向测距（DS-TWR）**，解决"靠近的是不是本人"；
- **毫米波雷达负责"在哪"**：探测车周所有行人的 X/Y 坐标，解决"人在什么方位、什么距离"；
- **关键在于交叉验证融合**：代码里用 **`|雷达测距 − UWB 测距| ≤ 0.8m`** 关联两路数据——**只有雷达目标的距离和 UWB 测得的车主距离对得上，才认定这个坐标就是持标签的车主本人**。单一传感器做不到"定位 + 鉴权"同时成立，**融合之后天然抗"陌生人蹭开门"**。

**创新二：真正的"无感" + 距离迟滞控制。**
开门、关门用**不同阈值**并配状态位形成**迟滞区间**，避免车主停在临界点时车门反复误触发；比遥控钥匙、机械钥匙乃至手机蓝牙钥匙都更"无感"。

**创新三：按方位分区的智能安防（分区电子围栏 + 分区录像 + 隐私友好）。**
- **象限分区触发**：车周按坐标象限分 4 区，**哪个方位越线只唤醒那一路摄像头**，而非四路全开——**省算力、省存储**；
- **"先录后判、按身份决定去留"**：先无条件录像，一旦人脸识别确认是车主就**自动删除**刚录视频，**只对陌生人留存证据**——兼顾取证与车主隐私。

**创新四：分布式多节点 + BLE 菊花链汇聚。**
3 个雷达分挂 3 块 ESP32、分装不同角度，经 **BLE 逐级级联**把多目标坐标汇聚到主控——**用低成本无线组网解决多雷达多方位覆盖的布线难题**，扩展性好。

**创新五：一套系统、四重冗余开门。**
**UWB 无感 + 人脸 + NFC + 按键**，四种入口互为备份：**追求极致无感体验的同时，标签没电、识别失败等极端情况仍有兜底**，可靠性拉满。

**创新六：IMU—云端联动的主动安防。**
把传统"事后查记录"的**被动安防**，升级为**剐蹭即预警**的**主动实时告警**。

> 一句话总结创新：**"融合鉴权保无感、分区取证保隐私、四重冗余保可靠、云端联动保主动"。**

---

## 六、技术难点与攻关（约 50 秒，视时间可删减）

1. **多传感器数据关联**：雷达坐标与 UWB 距离量纲、坐标系不同，我们通过距离阈值关联 + 状态位判定，解决"哪个雷达目标才是车主"的数据融合难题。
2. **多节点无线组网**：多雷达布线困难，采用 BLE 主从菊花链 `connectToSlave / notifyCallback` 逐级 notify 汇聚，稳定上报多目标。
3. **实时性与算力平衡**：ESP32 端做采集/预处理并用 **FreeRTOS 多任务**并行（UWB 测距、雷达接收、IMU 检测各占一任务），树莓派端做重负载识别，分层解耦。
4. **误触发抑制**：距离迟滞 + 状态位，避免临界抖动导致车门反复开关。

---

## 七、总结与展望（约 40 秒）

总结一下：本作品以**多模态融合鉴权**为核心，配合**分区安防、四重冗余、云端联动**，构建了一套**分布式、多模态的智能汽车无感交互与安防系统**，较好地解决了传统方案"无感不彻底、易被蹭开、安防被动"三大痛点。

未来我们计划：一是引入**轻量 TinyML 模型**在边缘端做行人意图 / 行为识别，进一步降低误触发；二是扩展 UWB 锚点实现**车内外厘米级定位**（如自动寻车、迎宾灯光跟随）；三是打通整车 CAN 总线，向量产形态演进。

**以上就是我们的全部汇报，感谢各位评委老师！恳请批评指正。**

## 附 B：答辩问答预案（评委高频提问）

**Q1：你们和特斯拉 / 蔚来等量产的手机蓝牙钥匙、UWB 数字钥匙有什么区别？创新性在哪？**
A：量产 UWB 钥匙主要解决"测距防中继"，本质仍是**单模态**——只知道"钥匙在附近"，**不知道靠近的这个人是不是拿钥匙的本人**。我们的创新在于**把 UWB 的"身份/距离"和毫米波雷达的"人体坐标"做交叉验证**（`|雷达距离−UWB距离|≤0.8m` 才放行），**同时完成定位与鉴权**，这是单模态方案做不到的，也是我们防"陌生人蹭开门"的根本。

**Q2：为什么用毫米波雷达而不用摄像头做人体检测？**
A：三点考虑：一是**隐私**——雷达只出坐标不出图像，日常监测不涉及隐私；二是**全天候**——雷达不受光照、雨雾影响，夜间同样工作；三是**低算力**——直接输出 X/Y 坐标，不需在边缘端跑重型视觉模型。摄像头我们只在**越界取证和人脸识别**时才按需唤醒。

**Q3：UWB 和雷达测距误差较大时，融合会不会误判？0.8m 阈值怎么定的？**
A：0.8m 是综合 DW3000 UWB 厘米级精度与 LD2450 雷达距离精度、并考虑人体是有体积的目标（不同传感器打到身体不同部位）实测标定出来的经验值——**太小会漏判本人、太大会放进旁人**。同时我们叠加了**距离迟滞 + 状态位**做时序确认，单帧异常不会直接触发开门，进一步抑制误判。

**Q4：BLE 菊花链会不会有延迟累积或断链问题？为什么不用 Wi-Fi/ESP-NOW？**
A：菊花链确实有级联延迟，但雷达坐标是**厘米级慢变量**、行人步速有限，当前 3 级级联延迟在可接受范围；断链我们靠重连回调 `connectToSlave` 恢复。选 BLE 是因为**功耗低、组网简单、成本可控**；ESP-NOW 是很好的演进方向，已列入后续优化。

**Q5：人脸识别用的什么方案？在树莓派上实时性如何？**
A：树莓派端用 Python `face_recognition` 库做车主比对。因为**人脸识别只在开门/取证瞬间按需触发**、不是常态视频流，所以对实时性要求不高，树莓派 5 的算力完全够用；日常监测是低算力的雷达在跑。

**Q6：剐蹭检测会不会误报（比如关门震动、有人靠一下）？**
A：我们用 MPU6050 检测**加速度突变**并设阈值，关门等常规震动幅度达不到触发线；后续可用**IMU 波形特征 + TinyML 轻量分类**进一步区分"剐蹭 / 正常震动"，这也是我们展望里提到的方向。

**Q7：标签没电、或车主没带标签怎么办？系统可靠性如何保证？**
A：这正是我们设计**四重冗余开门**的原因——**UWB 无感 / 人脸 / NFC / 按键**互为备份，任意一路失效都有兜底，兼顾"无感体验"与"极端可靠性"。

**Q8：整套系统成本大概多少？有没有量产可行性？**
A：核心是 6 块 ESP32（单价低）+ 1 块树莓派 + 若干消费级传感器，**整体成本可控**；架构上感知/中枢/执行三层解耦、节点可插拔，具备向车规形态演进的基础，后续打通 CAN 总线即可对接整车。

**Q9：多模态数据是怎么同步 / 时序对齐的？**
A：anchor 主控用 **FreeRTOS 多任务**分别跑 UWB 测距、雷达 BLE 接收、IMU 检测，各任务按自己周期采集，在主控侧做一次融合判定后再统一经串口上报，保证发给树莓派的是"已对齐、已判定"的结构化结果。

**Q10：这套系统的最大局限 / 你们认为还能怎么改进？**
A：坦率讲，当前融合判据偏"规则化"（阈值 + 迟滞），在复杂人群场景下鲁棒性还有提升空间。改进方向就是我们展望里的三条：**边缘 TinyML 做意图识别、扩展 UWB 锚点做厘米级定位、打通 CAN 走向量产**。
