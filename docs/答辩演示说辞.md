## 一、开场 1 分钟自述（逐字稿，卡 ≤60 秒）

> 【要点：通知要求这 1 分钟必须讲清——作品名称 / 用的开发板 / **板上完成的主要功能** / 应用场景与解决的问题 / 主要创新点。语速稳，念完即请演示。】

各位评委老师好！我们的作品是**《基于多模态感知的智能汽车无感交互与安防系统》**。

硬件上，我们用**一块树莓派 5 做中枢**、**六块 ESP32（含一块 ESP32-S3）做感知节点**。**ESP32 上**完成了 UWB 双向测距、毫米波雷达数据的 BLE 汇聚、MPU6050 剐蹭检测和 NFC 读卡；**树莓派 5 上**跑 Qt 车载界面、人脸识别和摄像头安防调度——**从底层采集到上层决策，都在这两类板子上闭环完成**。

它解决两个真实痛点：一是无钥匙进入**"不够无感、还容易被陌生人蹭开门"**；二是车被剐蹭时**"车主毫不知情、事后没证据"**。

我们的主要创新是：**用 UWB 测钥匙距离、毫米波雷达测真实人体位置，两者做'钥匙—人体一致性'校验**，既无感又能防中继、防蹭开；安防上做**"先监控、异常才录像"的分区取证**，再配合**剐蹭时 IMU 触发的微信秒级预警**。

下面请老师看现场演示。

> 【念稿约 55 秒。若组长已在倒计时，删掉"硬件上"整句里的细节、只留"树莓派5 + 六块 ESP32"，把时间留给演示。】

## 二、现场演示编排（约 6 分钟，按"先亮点后组合"排序）

> 【核心原则：按下面**既定顺序**演，形成"**看得见 → 查得到 → 进得去 → 兜得住**"的叙事线。每个动作配一句"边演边说"，并暗合评分维度。全程**不碰作品、不插线、不重启**。】

### 演示 1｜雷达检测人员 + 分区监控（开场，展示"看得见"）〔平台利用率 + 系统完整度〕

- **动作**：让一个人在车周走动——**Qt 界面实时标出行人的坐标、方位**；当人越过某方位警戒线，**对应象限那一路摄像头被唤醒、实时画面上屏**；人离开区域——**摄像头自动关闭**。
- **边演边说**："毫米波雷达在车周持续探测行人坐标，界面实时显示。有人越界，我们**只唤醒对应方位摄像头做实时监控**——注意，此时**只是监控、并不录像**，普通路人路过不留任何视频。"
- **踩点**：先亮出**感知层 + 车载 UI**，并埋下"**监控 / 录像分离**"的伏笔，为演示 2 做铺垫。

### 演示 2｜陌生人碰擦 → 录像取证 + 微信预警（"查得到"，最有冲击力）〔创新性 + 实用性 + 完整度〕

- **动作**：让**陌生人**在车边**碰擦/晃动车模**模拟剐蹭——这一下**系统才开始录像取证**，同时**几秒内演示者手机微信弹出预警**，把手机举给评委看。
- **边演边说**："关键区别在这——刚才只是监控，**一旦发生碰擦这种异常，车身 IMU 检测到加速度突变，系统才落盘录像取证、并经云平台秒级推微信**。**只有异常才录像**，既拿到证据又不产生冗余视频；人不在车旁也第一时间知情。"
- **踩点**：**"先监控、异常才录"**的分级安防 + **主动预警**一次演全。说法用**"剐蹭预警 / 取证"**，不说"防剐蹭"——物理刮蹭防不住，我们做的是发现+取证+通知。
- 【提示：需确保"碰擦→录像"联动已接好；黑名单人脸触发录像**如实说是规划中**。】

### 演示 3｜无感开关门 + 融合防蹭开（"进得去"，核心创新）〔创新性 + 实用性〕

- **动作**：演示者**带 UWB 标签**从远处走近约 1 米——**门自动开、绿灯亮**；走远 2 米外——**门自动落锁、红灯亮**。再让**不带标签的陌生人**走到车边——**门不开**。（"等"：随后可快演 **NFC 卡一刷 / 按标签按键**也能开。）
- **边演边说**："全程不掏钥匙、不碰车，靠近即开、走远即锁。凭什么陌生人蹭不开？——**UWB 测到我的钥匙在 1 米，毫米波雷达同时确认这个距离真的站着一个人，两者对得上才开门**，所以信号被中继、旁人贴身都蹭不开。另外还有 NFC、按键兜底。"
- **踩点**：**融合鉴权**是本作品最核心的创新，一句话点透即可，**别展开测距公式**；顺带把 NFC/按键组合快演，体现冗余。

### 演示 4｜人脸识别车主开门（压轴收尾，"兜得住"）〔完整度 + 可靠性〕

- **动作**：**最后**演——标签万一没带 / 没电，车主**正脸对准摄像头 → 识别通过 → 开门**。
- **边演边说**："这是我们的最后一道兜底——**UWB、人脸、NFC、按键四重冗余开门**，任意一路失效都能进得去，兼顾极致无感与极端可靠。"
- **踩点**：放在最后收束"**一套系统、四重冗余**"，体现工程完整度与可靠性。

### 贯穿全程｜Qt 车载 UI〔完整度 + 平台利用率〕

- 演示过程中**始终把 Qt 界面朝向评委**：实时显示**车门状态、车周行人坐标、四路摄像头开关、录像回放**。
- 一句带过："这块屏是树莓派 5 上的 Qt 界面，车周态势一目了然。"

> 【演示节奏兜底：若时间紧被示意加速，**务必保演示 2、3**（碰擦录像预警 + 无感开门融合鉴权，这是两大创新亮点）；演示 1 快速带过、演示 4 口头一句即可。】

## 三、随机质询问答预案（如实、简要，直对提问）

> 【规则：**只答被问的、一两句说清**，评委要深了再展开。以下按五大维度归类，加粗是必答核心。】

### 设计创新性

**Q：UWB 不就是认钥匙吗？它并不能识别"是不是车主本人"吧？**
A：**您说得对，UWB 认的是钥匙、不是人脸，本质是"持钥匙即授权"。** 我们的创新不在这、而在**融合**：UWB 给"钥匙的距离"，毫米波雷达给"车边真实人体的位置"，**只有两者对得上才开门**——这能挡住**信号中继攻击**（钥匙信号被放大到车边、但现场没人）和**旁人误触**。**"是不是本人"的强身份，由人脸识别那一路兜底**。三者叠加，才既无感又难冒用。

**Q：`0.8m` 这个融合阈值怎么定的？**
A：是综合 UWB 厘米级精度、雷达距离精度、再考虑**人体有体积**（不同传感器打到身体不同部位）实测标定的经验值——**太小会漏判本人、太大会放进旁人**；再叠加距离迟滞做时序确认，单帧异常不开门。

**Q：为什么陌生人越界只监控不直接录像？**
A：日常绝大多数是**无害路人**，一越界就录会产生**海量冗余视频、占存储也不利隐私**。所以越界**只实时监控**，**只有异常（剐蹭 / 规划中的黑名单人脸）才落盘**，关键证据不漏、路人不留存。

### 功能实用性

**Q：标签没电或没带怎么办？**
A：这正是我们做**四重冗余**的原因——**UWB / 人脸 / NFC / 按键**互为备份，任一路失效都有兜底。

**Q：剐蹭检测会不会误报（关门震动、有人靠一下）？**
A：用 MPU6050 检测**加速度突变**并设阈值，关门等常规震动达不到触发线；后续可用 IMU 波形 + 轻量分类进一步区分。

**Q：无感开关门会不会在临界点反复误触发？**
A：不会。**开门、关门用不同阈值 + 状态位形成迟滞区间**，车主停在临界点也不会反复开合。

### 工程可靠性

**Q：这么多节点和线，搬运振动会不会松？**
A：接插件都做了**固定与走线约束**，加电后**一次成型、演示全程不插拔**；节点间用无线，减少了硬连线松动的风险。

**Q：BLE 级联断了怎么办？**
A：有**重连回调**自动恢复；雷达坐标是慢变量，短暂断连不影响判定。

### 平台利用率

**Q：为什么用树莓派 5 + ESP32 两类板子，而不是一块搞定？**
A：**算力分层**——ESP32 贴近传感器做**实时采集与预处理**（UWB 测距、雷达汇聚、IMU 检测各占一个 FreeRTOS 任务并行跑），**树莓派 5 专注高算力的人脸识别、Qt 界面和调度**。**低算力管实时、高算力管决策**，既保实时又留扩展。

**Q：板上的资源都用起来了吗？**
A：用得比较满——ESP32 侧用到 **UWB、BLE、I²C（MPU6050）、SPI/UART、NFC、WS2812、FreeRTOS 多任务**；树莓派侧用到**摄像头、Qt/GPIO 串口、Python 视觉**，两类平台的核心外设基本都在工作。

### 系统完整度

**Q：整套系统是怎么串起来的？**
A：**感知层** 6 块 ESP32 采集 → **BLE 菊花链**汇聚到主控 → **UART 上传树莓派** → 树莓派 Qt **显示 + 调度** → 触发**开关门 / 分区监控 / 异常录像 / 云端预警**，形成"人—车交互"到"车—环境安防"的**闭环**。
